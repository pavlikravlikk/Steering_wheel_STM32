# STM32F3DISCOVERY Steering Wheel Controller

Our project implements a custom USB HID steering wheel controller using the **STM32F3DISCOVERY** development board (STM32F303VCT6) and a standard analog potentiometer. The repository contains the complete firmware project, created with STM32CubeMX, and a Python visualizer and demonstration game.

---


## Overview

The objective of this project is to create a responsive, low-latency, and jitter-free steering controller. An analog potentiometer works as the steering angle sensor, converting physical wheel rotation into an analog voltage. The microcontroller samples this signal via ADC1, processes it through a digital filter.

---

## Hardware Setup and Wiring

### 1. Potentiometer Pinout
A standard rotary potentiometer functions as a voltage divider. Connect the three terminals to the STM32F3DISCOVERY header pins as follows:

| Potentiometer Terminal | STM32F3DISCOVERY Header Pin | Function |
| :--- | :--- | :--- |
| **Terminal 1 (VCC)** | **`3V` or `3.3V`** | Reference voltage supply. |
| **Terminal 2 (Signal)** | **`PA1`** | Analog input connected to ADC1, Channel 2 (`ADC1_IN2`). |
| **Terminal 3 (GND)** | **`GND`** | Ground reference. |


### 2. Host Computer USB Connections
The STM32F3DISCOVERY board has two micro-USB ports:
- **USB ST-LINK (Connector CN1, top edge):** Connects to the on-board ST-LINK/V2-1 debugger for flashing firmware, hardware debugging, and board power.
- **USB USER (Connector CN5, bottom edge near user buttons):** Connects directly to the microcontroller USB peripheral. Connect this port to the computer so the operating system recognizes the board as a USB HID game controller.

## Signal Processing and Potentiometer Stability

Mechanical potentiometers have such problems: brush friction noise, contact bounce during motion, and jitter when stationary. Our firmware has a processing inside `Read_Potentiometer_Filtered()`:

```
[Analog Voltage on PA1]
           │
           ▼
1. Hardware Calibration (Startup offset compensation)
           │
           ▼
2. Oversampling (16 consecutive ADC samples per cycle)
           │
           ▼
3. Outlier Rejection (Discards 2 min and 2 max spikes)
           │
           ▼
4. Exponential Moving Average Filter (α = 0.25 via Cortex-M4 FPU)
           │
           ▼
5. Stationary Deadband / Hysteresis (Suppresses jitter < 4 ADC counts)
           │
           ▼
6. Boundary Clamping (Guarantees full 0 and 4095 range)
           │
           ▼
[USB HID Report Transmission]
```

### Details:

1. **Hardware Calibration (`HAL_ADCEx_Calibration_Start`):**
   Executed once at startup to calibrate the internal ADC linearity and offset.
2. **Oversampling:**
   Gathers a burst of 16 consecutive ADC samples in each cycle.
3. **Outlier Rejection and Trimmed Mean:**
   The 16 samples are sorted. The 2 lowest and 2 highest readings are discarded to eliminate spikes from mechanical contact imperfections. The remaining 12 samples are averaged.
4. **Exponential Moving Average:**
   $$S_t = S_{t-1} + 0.25 \cdot (X_t - S_{t-1})$$
   Calculated on the Cortex-M4 hardware Floating-Point Unit (`float`). Provides smooth tracking in both directions without integer underflow or lag.
5. **Stationary Hysteresis:**
   If the change from the last output is less than 4 ADC counts, the previous value is retained. This eliminates cursor trembling when the wheel is held still.
6. **Boundary Clamping:**
   Readings $\le 8$ are clamped to `0`, and readings $\ge 4087$ are clamped to `4095`, ensuring full lock-to-lock travel.

## Compiling the Firmware with CMake

The project uses the standard CMake structure generated by STM32CubeMX.

### Prerequisites (Ubuntu / Debian / WSL):
```bash
sudo apt update
sudo apt install -y gcc-arm-none-eabi libnewlib-arm-none-eabi ninja-build cmake
```

### Option 1: Using CMake Presets (Simplest, standard CubeMX method)
```bash
cd steeringwheel_firmware

# Configure using the Debug preset
cmake --preset Debug

# Build the binary
cmake --build --preset Debug
```

### Option 2: Using Direct CMake Commands
```bash
cd steeringwheel_firmware

# Configure
cmake -B build/Debug -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_TOOLCHAIN_FILE=cmake/gcc-arm-none-eabi.cmake

# Compile
cmake --build build/Debug
```

## Flashing the Microcontroller

Connect the **USB ST-LINK** port to your computer.

- **From WSL (using the Windows tool installation):**
  ```bash
  /mnt/c/ST/STM32CubeIDE_2.2.0/STM32CubeIDE/plugins/com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.win32_*/tools/bin/STM32_Programmer_CLI.exe -c port=SWD -w build/Debug/steeringwheel_firmware.elf -v -rst
  ```

```bash
openocd -f board/stm32f3discovery.cfg -c "program build/Debug/steeringwheel_firmware.elf verify reset exit"
```

## Running the Demonstration Application

The repository includes a Python visualizer and mini-game (`stm_32_wheel.py`) to verify potentiometer response in real time.
We used generative AI to create a python visualization.

### 1. Connection
Connect the **USB USER** port to your computer.

### 2. Install Python Dependencies
```bash
pip install pygame hidapi
```

### 3. Launch
```bash
python stm_32_wheel.py
```
